# Запуск в проде

Весь прод — один `docker compose` на одном сервере:

| Сервис | Что делает |
|---|---|
| `caddy` | единственный, кто слушает 80/443: HTTPS (Let's Encrypt, сам продлевает), отдаёт готовые фото с диска, остальное — `api` и `web` |
| `web` | Next.js: витрина, кабинет, админка |
| `api` | FastAPI (`WEB_CONCURRENCY` процессов) |
| `worker` | синхронизация с поставщиком и очередь фото |
| `migrate` | применяет миграции при каждом `up` и завершается; `api` и `worker` стартуют после него |
| `db` | Postgres 18, наружу не открыт |

Данные лежат в volumes: `pgdata` (база), `media` (обработанные фото), `caddy_data` (сертификаты).

Для разработки — [dev.md](dev.md).

## 1. Что понадобится

**Сервер.** VPS на Linux (Ubuntu 24.04 / Debian 13), x86_64, с белым IP.

| | Минимум | Удобно |
|---|---|---|
| CPU | 2 ядра | 4–8: снятие водяного знака — ~1 с процессора на фото, первая загрузка ~620 тыс. фото |
| RAM | 4 ГБ | 8 ГБ |
| Диск | 50 ГБ SSD | 80+ ГБ: фото ~50 КБ на штуку (две версии), всего ~30 ГБ; база несколько ГБ; запас под образы и бэкапы |

**Домен** с A-записью на IP сервера, например `shop.it-trade.ru`.

**Доступы:**

- логин и пароль b2b.i-t-p.pro: без них не будет каталога;
- почтовый ящик с SMTP: коды при регистрации и «Забыли пароль?». Без него в проде регистрация не работает. Для Яндекса и Mail.ru нужен пароль приложения, а не пароль от ящика;
- по желанию ключ [dadata.ru](https://dadata.ru) (бесплатно до 10 тыс. запросов в сутки): реквизиты организации по ИНН подставляются сами.

## 2. Подготовка сервера

Под root или через `sudo`:

```bash
# обновления, в том числе автоматические обновления безопасности
apt update && apt upgrade -y
apt install -y git curl unattended-upgrades
dpkg-reconfigure -plow unattended-upgrades

# Docker с плагином compose
curl -fsSL https://get.docker.com | sh

# файрвол: SSH, HTTP (нужен Let's Encrypt и редиректу на HTTPS), HTTPS и HTTP/3
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw allow 443/udp
ufw enable
```

Рекомендуется:

- **Вход по SSH только по ключу**: `PasswordAuthentication no` в `/etc/ssh/sshd_config`, затем `systemctl reload ssh`. Сначала проверьте, что вход по ключу работает.
- **Отдельный пользователь** для деплоя: `adduser deploy && usermod -aG docker deploy`. Группа начинает действовать после нового входа по SSH. Учтите, что группа `docker` по сути даёт root.
- **Ограничение логов Docker.** Без него логи контейнеров растут, пока не займут весь диск. Создайте `/etc/docker/daemon.json`:

  ```json
  { "log-driver": "json-file", "log-opts": { "max-size": "20m", "max-file": "5" } }
  ```

  и выполните `systemctl restart docker`. Настройка действует на контейнеры, созданные после неё.

- **Swap**, если памяти 4 ГБ: `fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile && echo '/swapfile none swap sw 0 0' >> /etc/fstab`.

Docker публикует порты в обход ufw, но наружу открыты только 80 и 443 у `caddy`: Postgres, API и Next.js доступны лишь внутри сети compose.

## 3. Код и `.env`

```bash
git clone <адрес репозитория> /opt/it-trade
cd /opt/it-trade
./prod-env.sh
```

Для приватного репозитория добавьте на сервер deploy key (ключ только на чтение) в настройках репозитория.

`prod-env.sh` готовит корневой `.env`, который читает docker compose:

| Что | Как заполняется |
|---|---|
| `POSTGRES_PASSWORD`, `JWT_SECRET` | генерирует случайные |
| `ADMIN_PASSWORD` | генерирует и показывает один раз в конце: сохраните в менеджер паролей |
| `IMAGE_WORKERS` | по числу ядер: ядра − 1, не больше 6 |
| `DOMAIN` | спрашивает и проверяет, что A-запись указывает на этот сервер |
| `ADMIN_EMAIL` | спрашивает, по умолчанию `admin@<домен>` |
| `SUPPLIER_LOGIN`, `SUPPLIER_PASSWORD` | спрашивает и пробует войти к поставщику |
| `SMTP_*`, `MAIL_FROM` | спрашивает и проверяет, открыт ли порт почтового сервера (многие хостинги закрывают исходящие 465/587, пока их не попросить) |
| `DADATA_API_KEY` | спрашивает, можно пропустить |

Скрипт не меняет уже заданные значения, поэтому его можно запускать повторно: он дозаполнит пустые поля и заново всё проверит. Прежняя версия файла сохраняется в `.env.bak`. `./prod-env.sh --yes` работает без вопросов: только генерация и проверки. В конце скрипт перечисляет, что ещё не готово. Остальные настройки описаны в комментариях `.env.example`.

Три значения нельзя менять бездумно:

- **`POSTGRES_PASSWORD`** задаёт пароль только при создании базы. Если поменять его в `.env` позже, API не сможет подключиться. Сменить пароль можно так: `docker compose exec db psql -U ittrade -c "ALTER USER ittrade PASSWORD '...'"`, затем исправить `.env`. Если `.env` потерян, а volume `pgdata` остался, скрипт не сгенерирует новый пароль, а попросит вписать старый.
- **`JWT_SECRET`**: при смене все пользователи выходят из аккаунтов.
- **`ADMIN_EMAIL` / `ADMIN_PASSWORD`** используются только при первом старте API, чтобы создать администратора. Потом пароль меняют в админке, и `ADMIN_PASSWORD` из `.env` можно стереть.

`.env` содержит все пароли. Скрипт ставит на него права `600`; не коммитьте его и храните копию в надёжном месте (см. «Резервные копии»).

## 4. Запуск

```bash
docker compose up -d --build
docker compose ps -a               # все Up, migrate — Exited (0)
docker compose logs -f caddy       # "certificate obtained successfully" для домена
curl https://<домен>/api/health
```

Первая сборка образов занимает несколько минут. Дальше:

1. Войдите в админку `https://<домен>/admin` под `ADMIN_EMAIL`.
2. Воркер сам скачивает категории и каталог (~390 тыс. товаров, ~3 мин), затем цены, остатки и списки фото (~20 мин). Ход видно в «Поставщики → IT Partner → Загрузка каталога».
3. На свежей установке загрузка фото стоит на паузе. Когда все проверки готовности там зелёные и пробная партия из 200 фото выглядит хорошо, нажмите «Начать загрузку фото».
4. Главные фото товаров в наличии (~121 тыс.) грузятся ~7,5 ч, после этого сайт можно открывать клиентам. Остальные фото догружаются в фоне ещё 1–2 суток.
5. В админке задайте наценки и контакты магазина.

Подробно порядок запуска описан в админке: «Как это работает → Загрузка каталога».

### Проверка перед открытием

- `http://<домен>` перенаправляет на `https://`, у сертификата нет предупреждений;
- регистрация на свою почту: код приходит, а не теряется в спаме (если попадает в спам, настройте SPF/DKIM для домена отправителя у почтового сервиса);
- «Забыли пароль?» присылает код;
- товары с фото и ценами, корзина, оформление заказа, заказ виден в админке;
- `docker compose logs --since 1h api worker | grep -i error` пусто или понятно.

### Пробный запуск без домена

С `DOMAIN=localhost` Caddy выпускает свой локальный сертификат: браузер предупредит о нём, но всё работает. Так удобно проверить сборку на своей машине и не упереться в лимиты Let's Encrypt (5 одинаковых сертификатов в неделю).

Пока домена нет, можно работать по IP сервера: `DOMAIN=203.0.113.10`. Сертификат тоже свой, у Caddy: браузер один раз предупредит, дальше сайт, вход и админка работают по HTTPS. Открывать нужно ровно `https://<этот IP>`. Вариант без HTTPS (`DOMAIN=http://…`) не поддерживается: Caddy с ним не запустится, а cookie входа в проде передаются только по HTTPS.

Когда появится домен: A-запись на сервер, домен в `DOMAIN`, `docker compose up -d`. Caddy сам получит сертификат Let's Encrypt; войти придётся заново, потому что cookie привязаны к адресу сайта.

## 5. Обновление

```bash
cd /opt/it-trade
git pull
docker compose up -d --build       # пересобирает образы, migrate применяет новые миграции
docker image prune -f              # удаляет старые образы
```

Пока собираются образы, старые контейнеры продолжают работать. Сайт недоступен только пока контейнеры пересоздаются и идут миграции: обычно секунды, до полуминуты. Если миграция упала, `api` и `worker` не стартуют: смотрите `docker compose logs migrate`.

Перед обновлением с новыми миграциями сделайте бэкап базы (ниже).

## 6. Резервные копии

**База** — главное, что нужно беречь: заказы, клиенты, организации, настройки.

```bash
mkdir -p /var/backups/it-trade
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > /var/backups/it-trade/db-$(date +%F).dump
```

Каждую ночь через `crontab -e` (знак `%` в crontab экранируется):

```cron
30 3 * * * cd /opt/it-trade && docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > /var/backups/it-trade/db-$(date +\%F).dump && find /var/backups/it-trade -name 'db-*.dump' -mtime +14 -delete
```

Копия на том же сервере не спасёт при потере сервера: раз в сутки отправляйте `/var/backups/it-trade` во внешнее хранилище (restic, rclone в S3 или на другой сервер). Туда же положите копию `.env`.

Восстановление:

```bash
docker compose stop api worker web
docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner' \
  < /var/backups/it-trade/db-2026-10-28.dump
docker compose start api worker web
```

**Фото** (volume `media`) бэкапить не обязательно: воркер скачает и обработает их заново, но на это уйдут сутки. Обязательно сохраните только перекалиброванные шаблоны знака, если вы их делали (`media/watermark/`, см. README):

```bash
docker run --rm -v it-trade_media:/m:ro -v /var/backups/it-trade:/b alpine tar czf /b/watermark.tgz -C /m watermark
```

**Сертификаты** (`caddy_data`) Caddy при потере выпустит заново.

## 7. Повседневное

```bash
docker compose ps                          # что запущено
docker compose logs -f --tail 100 api      # логи (api, worker, web, caddy, db)
docker compose restart worker              # перезапуск одного сервиса
docker compose exec worker python -m app.cli --help   # разовые команды: sync stock, reprice...
docker compose exec db psql -U ittrade     # консоль базы
docker stats                               # процессор и память по контейнерам
df -h /var/lib/docker                      # место на диске
```

После правки `.env` выполните `docker compose up -d`: compose пересоздаст контейнеры, у которых поменялись настройки. Простой `restart` новые значения не подхватит.

Контейнеры с `restart: unless-stopped` поднимаются сами после перезагрузки сервера и после падения.

## 8. Если что-то не так

| Симптом | Причина и что делать |
|---|---|
| Caddy пишет ошибки ACME, браузер ругается на сертификат | A-запись не на этот сервер, закрыт порт 80, или в Cloudflare включён прокси (оранжевое облако). Проверка — `./prod-env.sh --yes`. После исправления: `docker compose restart caddy` |
| `api` перезапускается, в логах `JWT_SECRET must be set` | пустой или короткий `JWT_SECRET`: `./prod-env.sh` сгенерирует новый |
| `password authentication failed for user "ittrade"` | `POSTGRES_PASSWORD` в `.env` не совпадает с паролем, с которым создана база: верните старый или смените пароль в базе (раздел 3) |
| Каталог не грузится, в логах воркера `login failed` | неверный `SUPPLIER_LOGIN` / `SUPPLIER_PASSWORD`; после исправления `docker compose up -d` |
| Коды не приходят, в логах API ошибки SMTP | неверный пароль (нужен пароль приложения), не тот порт (465 — TLS, 587 — STARTTLS) или хостинг закрыл исходящую почту |
| Сайт открывается, но показывает 502 | `web` или `api` не запущен: `docker compose ps` и логи этого сервиса |
| Кончается место | старые образы (`docker image prune -f`, `docker builder prune -f`), логи без ограничения (раздел 2), бэкапы |
