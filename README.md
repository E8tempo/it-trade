# IT Trade

Интернет-магазин (Крым) на каталоге поставщика [b2b.i-t-p.pro](https://b2b.i-t-p.pro/download/docs/api/api.html).

- **backend**: Python 3.14, FastAPI, SQLAlchemy (async), Alembic. Postgres в проде, SQLite в разработке.
- **frontend**: Next.js 16 и shadcn (`frontend/`, свой git-репозиторий). Пока каркас: прокси к API и JWT-сессии; в docker compose ещё не добавлен.
- **деплой**: `docker compose` + Caddy (HTTPS через Let's Encrypt автоматически).

## Запуск на сервере

```bash
cp .env.example .env      # DOMAIN, POSTGRES_PASSWORD, JWT_SECRET, ADMIN_EMAIL/ADMIN_PASSWORD, SUPPLIER_LOGIN/PASSWORD
docker compose up -d
```

Дальше:

1. `migrate` применяет миграции.
2. `worker` скачивает дерево категорий и каталог (~390 тыс. товаров, ~3 мин), затем цены и наличие и списки фото (~20 мин).
3. Загрузка фото на свежей установке стоит на паузе: она занимает часы, поэтому сначала проверка. В админке (`/admin`, аккаунт `ADMIN_EMAIL` создаётся при первом старте), «Поставщики → IT Partner → Загрузка каталога»: все проверки готовности зелёные, пробная партия из 200 фото выглядит хорошо — тогда «Начать загрузку фото».
4. Главные фото товаров в наличии (~121 тыс.) грузятся первыми: при 4,5 фото/с это ~7,5 ч, после этого сайт можно открывать. Остальные фото, до 8 на товар (~500 тыс.), догружаются в фоне ещё ~1–2 суток.

Ход загрузки, оценка времени и ошибки — там же, в «Загрузке каталога» поставщика; порядок запуска по шагам — в админке, «Как это работает → Загрузка каталога».

В `.env` только то, что фиксируется при развёртывании. Наценки, контакты и прочее, что меняется в процессе работы, лежат в БД (`site_settings`) и правятся через админку: наценки — по поставщикам (`/api/admin/suppliers/{code}/pricing`), контакты магазина — `/api/admin/settings/shop`.

Запуск для разработки (SQLite, выборка ~11.7 тыс. товаров): [docs/dev.md](docs/dev.md).

## Как устроено

```
          ┌──────────── Caddy :443 ─────────────┐
 /media/* │ файл есть → отдаёт с диска (immutable)
          │ файла нет → api (скачать, снять знак, сохранить)
 /api/*   │ → api (FastAPI)
 /        │ → (будет) Next.js
          └─────────────────────────────────────┘
 worker: категории/каталог раз в сутки, остатки каждые 30 мин, списки фото, очередь фото
 db: Postgres 18 (pg_trgm для поиска по подстроке)
```

### Авторизация

JWT: access-токен на 15 минут и refresh-токен на 30 дней, оба в httpOnly-cookies. Для API-клиентов токены также возвращаются в JSON.

- Refresh-токен ротируется при каждом обновлении. Если уже использованный токен предъявят повторно позже чем через 30 с, отзывается вся цепочка сессии.
- `frontend/proxy.ts` обновляет истёкшую сессию до рендера страницы.
- Роли: `customer` и `admin`. `/api/admin/*` доступно только админу.

Эндпоинты и детали: [docs/dev.md](docs/dev.md#авторизация-jwt).

### Клиенты, цены и заказы

Сайт работает только с бизнесом (B2B): с компаниями и ИП.

- **Гость** видит только вход и регистрацию: любую другую страницу `frontend/proxy.ts` отправляет на `/login?next=…`, а после входа возвращает на неё. Цен нет и в публичном API каталога.
- **Регистрация** — человек и его организация вместе: ИНН и название (КПП и остальное по желанию). Первый пользователь становится руководителем организации. Одна компания (ИНН + КПП) — одна запись: если она уже клиент, новых людей в неё добавляет менеджер.
- **До проверки** клиент видит каталог без цен и вкладку «Организации». Менеджер проверяет организацию в админке и заводит её договоры. После подтверждения открываются цены, корзина и заказы.
- **Кабинет** — тот же сайт с панелью слева: Главная (статусы, последние заказы, новости и акции), Каталог, Корзина, Заказы, КП и Взаиморасчёты (скоро), Организации, Профиль. Сверху в панели выбирается организация, от которой клиент работает: её цены, корзина и заказы.
- **Цены.** У товара четыре цены: розница и опт, каждая за наличные и безнал, со своими правилами наценки на каждого поставщика. Клиенты платят оптовые, розничные остаются для справки (позже — РРЦ в КП). Цены всегда считает сервер.
- **Заказ** оформляется от организации, по договору (если он есть) и запоминает её реквизиты и договор. Руководитель видит все заказы организации, закупщик — свои.

Эндпоинты: [docs/dev.md](docs/dev.md#кабинет-клиента-корзина-заказы-организации).

### Админка

`/admin` — панель управления. Вход учётной записью с ролью `admin`. Первый администратор создаётся при старте API из `ADMIN_EMAIL` / `ADMIN_PASSWORD`.

Разделы сгруппированы по работе: «Продажи» (обзор, заказы, клиенты, новости и акции), «Каталог» (товары и цены, поставщики), «Система» (лаборатория, документация, настройки).

- **Обзор** — открытые заказы, выручка и наценка за 30 дней, состояние каталога, обработки фото и синхронизации с поставщиком.
- **Заказы** — список с фильтром по статусам и поиском (в том числе по названию и ИНН организации), ручное создание заказа (по телефону). В карточке заказа: смена статуса с комментарием, история, состав, доставка, оплата и тип цен, скидка, наценка, реквизиты организации и договор. Цена и закупка каждой позиции запоминаются на момент заказа.
- **Клиенты** — организации, зарегистрированные на сайте: проверка (подтвердить, отклонить с причиной), правка реквизитов, сотрудники и их роли (руководитель, закупщик), договоры (номер, дата, предоплата или отсрочка), заказы организации.
- **Новости и акции** — записи для главной страницы: черновик, публикация, закрепление, последний день акции.
- **Товары и цены** — закупка, РРЦ, четыре цены и наценка по каждому товару. Любую из цен можно зафиксировать вручную, товар — скрыть с сайта.
- **Поставщики** — свой раздел на каждого поставщика (пока IT Partner), потому что каталог каждый поставщик отдаёт по-своему:
  - **Цены** — правила для каждого из четырёх типов цен: общая наценка, наценки по категориям (наследуются вниз по дереву), минимальная наценка в рублях, округление, РРЦ. Перед сохранением видно, как изменятся цены.
  - **Загрузка каталога** — проверки готовности к запуску, этапы загрузки с прогрессом и оценкой времени, пробная партия фото, пауза, лимит фото на товар и скорость загрузки, фото с заметным следом знака и с ошибками.
- **Лаборатория** — снятие водяного знака на любом фото с разбором каждого шага, калькулятор цены.
- **Как это работает** — статьи об алгоритмах с формулами (KaTeX): водяной знак, его поиск и снятие, калибровка, конвейер фото, цены, синхронизация.
- **Настройки** — название, контакты и часы работы магазина, фильтры галереи.

Всё, что меняется в процессе работы (наценки, контакты, статусы заказов, организации), хранится в базе, а не в `.env`.

### Данные поставщика и лимиты

| Что | Откуда | Лимит | Как часто берём |
|---|---|---|---|
| Дерево категорий (4.4 тыс.) | `catalog_tree_N.json` | 1/мин | раз в сутки в 05:00 (настраивается в админке) |
| Каталог (~390 тыс., 125 МБ) | `products_N.json` | 2/час | раз в сутки, потоково через ijson |
| Цены и остатки (~172 тыс. в наличии) | `get_active_products` | 10/час | каждые 30 мин (настраивается в админке) |
| Списки фото | `read_new`, ≤100 SKU | 2/с | новые товары; товары в наличии раз в 14 дней |
| Сами фото | `/product_images/...?size=original` | 5/с | очередь: воркер (3/с, настраивается в админке), остальное — API для фото «по требованию» |

Все товары лежат в БД: так работают фильтры, поиск, фасеты и сортировки, а 390 тыс. строк для Postgres — немного. На витрине показываются товары в наличии; скрытые и пустые категории не выводятся.

### Фото: снятие водяного знака

Поставщик накладывает полупрозрачный серый знак «IT Partner»: `J = α·W + (1−α)·I`. Маска `α` и цвет `W` (≈31) восстановлены по ~800 фото поставщика. Значит, исходное фото восстанавливается точно, инверсией смешивания, а не дорисовыванием нейросетью: `I = (J − α·W)/(1−α)`. Подробности в [watermark.py](backend/app/images/watermark.py).

Что выяснилось о знаке:

- он рисуется по центру в пикселях исходника, тремя размерами по ширине картинки:
  - ≥~700 px — большой;
  - ~480–720 px — средний;
  - ~290–520 px — малый (в том числе на фото 300×300);
- если высота больше примерно 2× ширины, знак повёрнут на 90°, и размер выбирается по высоте;
- на фоне темнее самого знака он не затемняет, а осветляет. Детектор это учитывает (согласованный фильтр с локальным фоном);
- цветность JPEG (4:2:0) хранится в половинном разрешении, поэтому Cb/Cr восстанавливаются отдельной маской: без этого остаётся цветная кайма;
- на части фото знак наложен 2–3 раза подряд. Такие знаки снимаются послойно;
- на части фото знак темнее, вплоть до чёрного, и тогда он ещё и бледнее (~90% плотности). Поэтому модель знака (число слоёв, плотность, цвет) подбирается под каждое фото по краям штрихов: так, чтобы после снятия они стали такими же ровными, как фото вокруг. Ровного фона для этого не нужно, подбор работает и на ткани. Из нескольких вариантов берётся тот, что оставляет меньше всего знака, отдельно над тёмными и светлыми частями фото;
- резкие края товара вдоль штрихов иногда сбивают детектор на 1 px, и буквы остаются «выдавленными». Поэтому соседние позиции сравниваются по тому, сколько резких перепадов остаётся на краях штрихов, и берётся явно лучшая (3 фото из ~700). Если поставщик пересчитал фото уже после наложения знака, знак может стоять между пикселями; так же проверяются и сдвиги на полпикселя (1 фото из ~720);
- у букв знака есть тонкая тёмная обводка. На белом она неотличима от плотного серого, а над тёмным товаром оставляла тонкий контур букв. Её калиброванная модель (кривая пропускания и цвета по прозрачности шаблона, по ~1450 фото) применяется, только если заметно уменьшает контур: это 47 фото из ~2000, остальные снимаются как раньше, до бита;
- часть фото обрабатывали уже после наложения знака (пересжатие, повторный знак), и точной модели для них нет: остаются бледные контуры. На ровных поверхностях они в конце дорисовываются по окружающему фону. На текстуре и у краёв товара этот шаг не работает, чтобы не стереть детали.

Качество на выборке (~810 реальных фото поставщика):

- знак находится у **99%** фото, где он должен быть;
- след знака после снятия (вдоль краёв штрихов, в уровнях яркости на единицу непрозрачности; до снятия медиана ~120): медиана 0.7, p99 4.9. Больше 10 (обычно это уже различимые буквы) — у 4 из ~2000 фото: ткань, мелкие рёбра и хром, где собственные края фото завышают оценку (до перехода на подбор по краям штрихов таких было 104);
- на чисто белом фоне отклонение после снятия: p99 = 0, p99.9 = 3 уровня из 255;
- скорость ~20 мс на детекцию и ~370 мс на снятие (обе модели знака, у ~30% фото одна), медиана ~500 мс на фото вместе с декодированием, проверкой остатка знака и двумя WebP.

Примеры «до/после»: [docs/watermark-before-after.jpg](docs/watermark-before-after.jpg).

Известные ограничения:

- примерно у 1% фото знак не находится: картинки уже ~290 px, узкие баннеры (например, 716×107), почти чёрный знак на чёрном товаре. Знак на таких фото остаётся;
- на фото 300×300 и на двойном знаке поверх текстуры или ярких градиентов может остаться бледный след: доводка по фону там не работает;
- на паре фото поверх обычного знака стоит второй, крупнее и в другом месте (например, большое «Partner»). Его модель не описывает, и он остаётся;
- **малый вариант** откалиброван по небольшой выборке, на однородных цветных фонах иногда виден бледный контур. Лечится перекалибровкой на данных из прода:
  ```bash
  docker compose exec worker python -m app.cli watermark-sample /tmp/wm 3000
  docker compose exec worker python -m app.cli watermark-calibrate /tmp/wm   # пишет в volume media/watermark/
  docker compose restart api worker
  docker compose exec worker python -m app.cli requeue-images small          # переобработать малый вариант
  ```
- на части фото поставщика есть **непрозрачная надпись `www.i-t-p.pro`** в углу. Она запечена в сам снимок, это не знак. Её можно только закрашивать (inpaint), пока не сделано.
- Фото без знака получить нельзя: публичного пути нет, партнёрский `read_internal_marketplace_images` для нашего аккаунта возвращает пустой список, а `read_client_images` отвечает «Отсутствует доступ». Проверить заново: `python -m app.cli probe-marketplace-images <sku>`.

### Хранение фото

- Метаданные лежат в БД (`product_images`: статус, размеры, какой вариант знака найден, сколько знака осталось, версия обработки), файлы — на volume `media`: `products/<id % 1000>/<id>_{lg,md}.webp` (1000 px для страницы товара, 480 px для карточек, корзины и поиска).
- Исходники берём в `original`: это самое большое, что есть у поставщика, обычно больше 800 px. `large` — то же фото, пересчитанное к 800 px: маленькие оригиналы там просто растянуты, а знак размыт пересчётом. Снятие знака идёт в исходном разрешении, уменьшаем уже сами.
- Главное фото товара — то, что поставщик пометил `is_main`; оно всегда на позиции 0.
- В галерее поставщика бывают повторы: тот же набор фото в двух размерах, рекламный слайд на шести языках. После обработки фото товара сравниваются по уменьшенным копиям 16 × 16, и из одинаковых показывается самое крупное (`duplicate_of`). Дополнительные фото меньше 400 px по длинной стороне не показываются. Размер и выключатель — в настройках админки. На dev-выборке скрыто 115 из 1357 фото, подробности — в админке, «Как это работает → Конвейер фото».
- Грузятся и показываются только первые 8 фото товара (настраивается в админке): у 10% товаров 15 фото и больше, и почти всё сверх 8 — повторы и слайды. Каталог на 13.10.2026: 171 тыс. товаров в наличии, 121 тыс. из них с фото, в среднем 6 фото на товар, ~54 КБ на фото в обоих размерах:

  | Объём | Фото | Диск | При 3 фото/с | При 4,5 фото/с |
  |---|---|---|---|---|
  | Главные фото товаров в наличии | ~121 тыс. | ~6,5 ГБ | ~11 ч | ~7,5 ч |
  | До 8 фото на товар | ~500 тыс. | ~27 ГБ | ~2 суток | ~1,3 суток |
  | Все фото тех же товаров | ~730 тыс. | ~40 ГБ | — | — |

- Заполнение упирается в лимит поставщика: 5 фото/с на всех. Воркер берёт столько, сколько задано в админке (до 4,5), остальное остаётся API для фото, открытых раньше, чем до них дошла очередь. Порядок: все главные фото, потом все вторые, третьи и так далее. Обработка — ~0,5–1 с процессора на фото, так что `IMAGE_WORKERS` нужен около числа ядер.
- У каждого фото записана версия обработки. Когда она растёт, фото старых версий переобрабатываются сами, после новых, а до замены на сайте видны старые.
- Фото товаров не в наличии по умолчанию обрабатываются только при первом просмотре (`IMAGE_PREFETCH_OUT_OF_STOCK`).
- Если поставщик меняет фото, у записи растёт `version`, и URL меняется (`?v=`), так что кеш браузера сбрасывается корректно.

## Разработка

Как запускать backend, воркер и frontend локально: [docs/dev.md](docs/dev.md).

CLI (`python -m app.cli --help`):

| Команда | Что делает |
|---|---|
| `sync categories\|products\|stock\|images` | запустить синхронизацию сейчас |
| `import-categories FILE`, `import-products FILE` | импорт уже скачанного JSON |
| `process-images N` | обработать N фото из очереди |
| `reprice` | пересчитать розничные цены |
| `requeue-images [big\|mid\|small]` | поставить готовые фото в очередь на переобработку |
| `dedupe-images` | найти повторы среди уже обработанных фото (новые фото проверяются сами) |
| `watermark-test IN.jpg OUT.jpg` | снять знак с локального файла |
| `watermark-sample DIR N`, `watermark-calibrate DIR` | перекалибровка шаблонов знака |
